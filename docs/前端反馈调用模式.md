# 前端反馈调用模式

更新日期：2026-10-04。

## 契约与使用

复用现有 `call_tool(toolset, tool, arguments, source=None, delivery=None)` Dispatcher。`delivery` 是调度元数据，不塞入目标工具的业务参数；厂商 Native Toolcall 仍正常输出函数名和 arguments。

```json
{
  "name": "call_tool",
  "arguments": {
    "toolset": "example",
    "tool": "test",
    "arguments": {"text": "业务参数"},
    "delivery": {"mode": "frontend_feedback", "trigger": "next_speech_start", "once": true}
  }
}
```

- `mode`: `immediate` 立即执行，或 `frontend_feedback` 先登记、由前端反馈触发。
- `trigger`: 默认 `next_speech_start`，也可 `manual`（仅按钮触发）。
- `once`: 严格布尔值。默认工具配置显式带 `once: true`；显式 delivery 省略 once 时为 false，可无限次触发，但同一时刻只允许一次执行。once 的“一次”指一次获接纳的尝试，失败、拒绝审批或派发失败也占用次数，不自动重试副作用。
- 完全省略 delivery 或传 null 时继承工具默认配置；显式 delivery 整体覆盖，不合并默认 once。没有工具默认配置时立即执行。
- `avatar_scene.avatar_set_pose` 默认 `{mode: "frontend_feedback", trigger: "next_speech_start", once: true}`。业务工具仍可直接使用原参数，Native 和普通软工具入口共用默认配置；通过 call_tool 的 `{mode: "immediate"}` 可覆盖。其他工具保持立即执行。

工具默认值放在 `@MethodDoc.builtin_tool(delivery=...)` 或工具集默认元数据中；Runtime Definition 传递该值。通用 Dispatcher 支持已有 builtin 与 MCP，不能把 framework 控制工具间接交付。不要为此另建工具执行系统。

## 时序与权限

1. 原模型工具调用经过既有权限流程。Dispatcher 解析 live ToolRef、检查本轮 enable_tools 并使用 Native Schema 校验参数。
2. 前端反馈模式只在后端 Redis 登记 intent，给模型返回 `status=scheduled, executed=false`，不等待 TTS。模型继续给出简短自然回复，不解释登记、工具返回或执行状态；不要声称未播放的动作已完成。
3. 工具卡片出现“触发调用”按钮。可手动触发；语音实际播放到该卡片后第一段可朗读文字时自动触发。卡片标记及工具内部不可读内容不进入 TTS；支持明确允许 TTS 的嵌套 Markdown replacement。
4. 浏览器 TTS 在真实 utterance 开始回调触发；后端合成音频在本地 Audio 的 onplaying 触发。下载、生成、入队、暂停和仅显示高亮都不会触发。相同播放请求内对工具 ID 去重；取消后不执行未播放到的调用，不遍历补执行全部剩余工具。
5. 前端请求仅有 `{msgid, toolid}`。事件为 `frontend.feedback.trigger`（手动）、`frontend.feedback.speech`（语音）、`frontend.feedback.status`（查询）。用户、对话及连接来自认证控制通道；不能接收前端工具名称、参数、delivery、代码或任意执行内容。
6. 后端按用户 + 对话 + msgid + toolid 查找 intent，锁内认领，统一限制 once 与并发；Celery 重投同一 execution_id 也不能执行第二次。语音触发仅允许登记时的原控制连接，避免刷新自动执行历史调用；按钮可绑定当前认证连接。
7. 独立 Worker 再检查消息存在、工具分配与当前权限，复用 ToolApprovalPolicy 和 managed ToolCall/preflight/资源守卫。重新触发不继承过去的单次审批；需要审批的工具仍需审批。自动语音请求超过 15 秒不补执行，审批等待也受该截止约束；实际执行有 30 分钟上限。
8. 执行使用独立 run，不启动第二轮模型、不改写原 assistant 回复、不添加第二份 Native tool_result。`frontend.feedback.updated` 广播轻量状态，revision 防止查询/认领回复晚到覆盖完成状态。

## 实现边界

- 后端 `application/frontend_feedback/` 负责 delivery 与 intent；`application/router/websocket/frontend_feedback.py` 负责认证定位入口；`application/workers/text_generator/frontend_feedback.py` 复用既有执行与审批。
- 前端 `src/features/chat/speech/` 负责反馈按钮和播放去重；`speechContent.js` 保留零宽执行锚点，在分段时关联下一段语音；`useChatSpeech` 接真实播放回调，StatusWidget 复用 shadcn Button 展示。
- intent 与 once 状态保存于服务端 Redis，TTL 为 7 天，不自动续播历史。Redis 被清空或 intent 到期后按钮显示已过期。这是当前版本的存储边界，不能从历史卡片中重新构造参数来规避它。
- 前端反馈适合动作、界面副作用等无需把执行结果反馈给当前 LLM 的工具。需要先查询结果才能组织回复的工具应使用 immediate。
- 维护时测试参数拒绝、越权、刷新、一次/无限、并发与重投、实际音频触发、暂停与取消、流式/最终分段一致性；修改后用 Black/Prettier 格式化。

部署需要重启 API 和 Celery Worker；Worker 使用 threads/prefork 并发至少 2（开发建议 4），或使用具有空闲消费能力的独立 Worker。单并发/solo 不适合语音同步投递；自动请求超过 15 秒会过期。反馈 run 不提供聊天消息流，不参与新回合互斥，但审批仍可通过已有界面恢复。
